# 银行智能客服助手：阶段里程碑需求计划书

版本：1.2｜编制日期：2026-11-12｜修订日期：2026-11-12｜状态：需求计划，尚未实施

面向读者：项目负责人、DeepSeek 执行模型、后续维护者。

## 1. 先读这一页

目标：把现有个人开发原型完善为银行内部坐席辅助与会后文本质检系统，先完成可复现演示，再完成生产就绪验证，形成可公开演示、可复现、可核查证据的个人工程项目。

**项目性质（v1.1 明确）**：这是个人展示项目，面向求职汇报。没有真实业务方、没有银行系统接入、没有生产部署许可。因此不得出现「生产使用」「服务多少坐席」「效率提升多少」这类表述。

用户已经确认：

- 使用者为内部坐席和质检人员；回答由坐席确认后使用。
- 首版覆盖银行卡挂失咨询、信用卡费用／还款咨询、投诉受理。
- 允许调用云模型（DeepSeek 官方为主，第三方中继仅作对比；费用上限 200 元/月）；应用代码在本机与 Ubuntu 之间按 SHA 同步。
- 数据处理、数据集构建、评测、模型微调在 Ubuntu 执行。
- 原项目仅到个人开发阶段，且用户已从银行离职；本轮工作单独记录为后续工程完善。
- **不得使用任何原银行内部资料，包括凭记忆复述的制度、话术与工单样式**；知识只来自公开监管条文与自造的演示制度。

两个完成层级必须分别验收：

| 层级 | 达成条件 | 可以对外描述 |
|---|---|---|
| 可演示 | M0—M5通过，真实模型参与，业务流程可操作 | 完成本地部署与端到端演示 |
| 生产就绪 | M6—M7通过，具备评测、权限、恢复和发布能力 | 完成生产就绪验证（工程实践层面） |

M8（业务试点与生产使用）不再是里程碑，移入文末附录A：没有业务方时该层级永久不可达，把它留在主线会诱使执行者用合成数据伪装上线。Ubuntu 是本机家用桌面机（`jack@192.168.1.27`），不自动等于任何生产环境；所有业务数据必须是合成数据。

## 3. 产品需求与范围

### 3.1 用户与工作流程

| 角色 | 主要操作 | 结果 |
|---|---|---|
| 坐席 | 载入会话、获取候选答复、查看引用、修改与采纳 | 有依据的答复建议与采纳记录 |
| 质检员 | 查看风险线索、核对原文和规则、逐项确认或驳回 | 有理由的人工复核结论 |
| 知识维护员 | 维护知识草稿、提交审核、提出更新 | 待审核知识版本 |
| 业务审核员 | 核对知识和规则、发布或退回 | 可使用的正式版本 |
| 管理员 | 账号、权限、部署配置、运行状态管理 | 可管理的运行环境 |

演示可以由一个人切换角色。生产权限由后台校验，角色不是可由前端随意传入的身份字段。知识编写者与发布审核者在生产流程中分离；管理员不自动绕过业务审核。

### 3.2 功能需求编号

| 编号 | 必须实现的功能 | 主要里程碑 |
|---|---|---|
| FR-01 | 登录、角色权限、会话访问范围 | M2、M5、M7 |
| FR-02 | 知识导入、来源、版本、审核、发布、失效 | M2、M3 |
| FR-03 | 会话文本/JSON导入、稳定轮次、原文保存 | M1、M2 |
| FR-04 | 核心诉求提取、业务过滤、检索及引用 | M3 |
| FR-05 | 带依据的候选答复、拒答/转人工、坐席采纳 | M3、M5 |
| FR-06 | 规则驱动的风险发现、证据定位、不确定状态 | M4 |
| FR-07 | 逐项复核、改判理由、状态持久化、防并发覆盖 | M4 |
| FR-08 | 真实报告查询与导出、历史追溯 | M4、M5 |
| FR-09 | 固定评测、基线比较、失败分析、可选微调实验 | M6 |
| FR-10 | Ubuntu部署、代码一致性、监控、备份恢复、回滚 | M0、M7 |

首版不接入真实账户交易；不执行挂失、转账、调额、退款、贷款审批；不自动对外发送消息。投诉受理在首版指识别诉求、整理受理摘要和给出人工处理指引，不表示已经接通银行工单系统。语音识别、自主多Agent、全量营销/催收、跨银行多租户不属于首版。

### 3.3 三个可验收业务故事

**S1 挂失咨询**：客户说“卡找不到了，手机银行也登不上”。系统识别咨询意图，检索当前有效的演示制度，给出渠道和后续步骤，明确这里只提供咨询。资料缺失时转人工。验收：引用可打开、过期版本不命中、不会声称已办理挂失。

**S2 费用／还款咨询**：客户质疑一笔费用。系统先区分费用说明与退款诉求；缺少卡种等必要条件时追问；只依据有效条款给出解释。验收：无条款支持时不编造费率、减免或审批结果；情绪只影响表达，不覆盖业务事实。

**S3 投诉受理**：客户明确表达投诉，坐席回复“不可能处理，你别再打了”。系统定位相关轮次、说明风险依据，生成待人工确认的摘要；质检员可驳回误报。验收：展示原文、规则版本、人工理由及处理历史；不虚构已建立银行正式工单。

所有示例中的制度、时限和费用必须来自有来源的知识，或明确标注为虚构演示制度。演示规则的风险命中不等于正式法律违规认定。

## 4. 工程边界与环境分工

### 4.1 默认技术路线

- 后端沿用现有 FastAPI 实现，但整体迁到 `src/bank_assistant/`（`src` 布局）；旧 `learn_20260210/app` 路径不再作为入口（ADR-0001）。
- Python 3.13；依赖统一由 `uv` 管理（`pyproject.toml` + `uv.lock`），根目录唯一入口；现有两份不一致的 `requirements.txt` 合并后删除。
- PostgreSQL 18 是业务事实存储，**只部署在 Ubuntu 的唯一实例**；Mac 不安装、不创建、不启动本地 PostgreSQL，通过 SSH 本地端口转发访问（ADR-0006 取代 ADR-0002 的本机部署部分）。Chroma 作为可重建检索索引，SQLite 仅用于单元测试替身。
- 前端 React + TypeScript + Vite，独立 `web/` 工程；首版只做三个页面（坐席工作台、质检复核、系统版本/评测）。
- 默认容器部署（`deploy/`）。先使用单一应用服务、单独任务worker和持久化数据库；可采用PostgreSQL任务表与租约实现简单异步任务。需要Redis/Celery等时再以实测理由引入。
- 构建产物与镜像在 Mac 上构建或只在容器内构建：Ubuntu 无 node/npm（ADR-0003）。
- 模型通过统一适配层接入：生成默认 DeepSeek 官方 `deepseek-chat`，第三方中继仅作对比与回退；embedding 自托管 `BAAI/bge-m3`（1024 维），索引带校准向量哈希以自证模型未漂移。SDK 缺失或凭据缺失应启动失败或报告能力不可用，不能自动返回随机向量（ADR-0004）。
- 此选型是本计划的默认实现路径，尚未部署；M0可依据资源调整并记录ADR。

### 4.2 双机代码与数据规范

Git 中的单一仓库和提交 SHA 是核心代码事实源。应用、前端、规则定义、提示词、训练与评测脚本、迁移、部署文件均纳入版本控制；数据集、模型权重、凭据、运行日志放 Ubuntu 仓库外。远程为 `github.com:kenneys-bot/agent_study_workspace`（**公开仓库**，因此仓库内不得出现任何敏感信息）。

**同步是单向拉取（ADR-0003）**：本机实现并测试 → 提交任务范围内变更 → push 到远程 → Ubuntu 用 HTTPS `fetch` 指定 SHA → 检出干净工作树 → 执行数据/评测/训练 → 记录代码 SHA 与产物版本。Ubuntu 不持有任何写凭据，也不在服务器上改主干；确需在服务器验证的改动，由负责人带回本机合并后再推送。运行实验前两端验证 SHA 一致、工作树干净。

同步是每次实验和发布前的版本一致性，不是实时覆盖文件。禁止双向 rsync 覆盖源代码、复制整个虚拟环境、强制重置用户未提交修改。已有改动由负责人认领；执行模型只提交自身任务涉及的内容。

凭据（SSH 私钥、云模型 key、服务器 sudo 密码、GitHub token）一律不进仓库、不写进提交信息、不写进日志或文档；配置只留占位值。

**数据驻留与数据库访问（ADR-0006）**：业务数据库的唯一实例在 Ubuntu；Mac 只保留小型合成夹具、脱敏报告与查看工具，不部署数据库。Mac 上的迁移、集成测试、演示、备份与恢复验证都经 SSH 本地端口转发访问服务器（`127.0.0.1:15432 → 服务器 127.0.0.1:5432`），PostgreSQL 不暴露到局域网或公网。同一实例按用途分库隔离：`bank_assistant_dev`（开发）、`bank_assistant_demo`（演示，自动化测试不得清空）、`bank_assistant_test`（集成测试）、`bank_assistant_restore_check`（恢复验证独立目标）。服务器或隧道不可达时，需要真实数据库的任务必须显式失败或标记 BLOCKED，**不得静默切换到 SQLite 或 mock 后宣称验收通过**。

Ubuntu 实测（2026-11-12，只读探测）：Ubuntu 24.04.3、Ryzen 7 5800X3D 8C/16T、62 GiB RAM、RTX 3060 Ti 8GB、`/` 剩 149G、Docker 29.0.1 免 sudo、**无 node/npm**、GitHub HTTPS 可用而 SSH 不可用；GPU 常态被另一训练任务占用，视为分时借用。以下为默认布局：

```text
~/projects/agent_study_workspace/       # Git checkout
~/bank-assistant-data/                 # DATA_ROOT
  raw/ curated/ splits/ manifests/     # 数据与拆分记录
~/bank-assistant-artifacts/            # ARTIFACT_ROOT
  evals/ runs/ models/ exports/        # 评测、训练、权重、导出
~/bank-assistant-backups/              # 独立备份；生产还需独立故障域副本
```

本机仅保留小型合成测试夹具、脱敏报告和展示所需内容。批量抓取/清洗、标注集构建、embedding建库、正式评测、微调和推理压测均在Ubuntu运行。本机单元测试与少量演示调用不受此限制。大型模型、生产数据和训练数据不得提交Git。

### 4.3 未知条件的处理

M0先自动探测可访问环境：Ubuntu版本、CPU/RAM/磁盘、GPU/显存/CUDA、容器运行时、网络、Git与可用端口；Mac 侧不探测本地数据库（不部署），改为探测 SSH 隧道与目标数据库的可达性。SSH地址、用户、访问方式、云模型凭据与费用上限由负责人通过安全配置提供；禁止在计划书或日志粘贴密钥。

服务器已可访问（ADR-0003），不再有 BLOCKED 前提；但重启整机必须逐次获得负责人准许。GPU 存在却被另一训练任务占用，微调以硬件检查结果与空闲窗口决定，不预选无法运行的模型。

## 6. 分阶段执行要求

### M0：建立可重复的开发基线与双机同步

入口：读取现状分析与当前代码；检查已有修改，不安装未经确认的全局依赖。

任务：

1. M0-01：记录仓库分支、SHA、未提交文件及范围；核对Python、容器和依赖清单，确定唯一依赖管理入口与锁文件。
2. M0-02：探测两端资源，建立 `.env.example`、本地/Ubuntu配置模板；配置样例只用占位值。默认服务仅对本机或受控私网开放。
3. M0-03：建立Git共享远程与同步脚本的dry-run；在双方干净checkout检出同一SHA并生成同步记录。无需覆盖现有工作目录。
4. M0-04：创建 `docs/implementation-status.md`、`docs/environment.md`，记录逐任务状态、环境阻碍和里程碑验收阈值；在 `docs/adr/` 记录数据库/索引、同步、数据驻留等实质权衡。
5. M0-05：梳理统一运行入口，计划新增Makefile或等价脚本。本文后续以 `make` 命令作为目标接口；先创建命令再运行，README须与真实命令一致。

交付：环境表、锁定依赖方案、双机同步说明、配置模板、状态文件、必要ADR。

验收：两端报告同一SHA；没有覆盖现存改动；凭据不在Git；Ubuntu数据目录可读写；未知条件有负责人和影响范围。Ubuntu未接通时只允许标记本机子任务完成。

### M1：修复后端并消除伪成功

入口：M0本机开发基线可用；历史发现以当前复现为准。

任务：

1. M1-01：修复默认意图类别、话术格式化、自定义数量/语气参数、相似问过滤误用旧库等问题。
2. M1-02：修复检索嵌套列表、上下文传递、重排结果数量、过滤条件传递、system消息丢失；验证实际调用参数。

### M2：建立业务事实存储、权限和版本

入口：M1通过；必须读取系统契约。

任务：

1. M2-01：实现契约中的实体和数据库迁移；数据库记录是业务事实源，索引可由有效知识版本重建。
2. M2-02：实现登录、服务端身份、角色与资源访问范围；默认演示数据也经过真实权限校验。密码使用成熟库哈希，禁止明文存储。
3. M2-03：实现知识草稿/审核/发布/退役；发布者分离；记录生效与失效时间、来源、适用业务和版本。
4. M2-04：实现会话与轮次导入、最小化敏感信息展示、追加式审计记录、UTC存储与前端本地时间显示。
5. M2-05：提供任务状态、幂等键、事务边界和并发版本控制基础；耗时模型调用不持有长数据库事务。

### M3：完成有依据的坐席辅助

入口：M2通过；业务知识只用合成或有出处的公开资料。

任务：

1. M3-01：在Ubuntu构建至少30条已审核演示知识，三场景各不少于10条；另加草稿、过期、冲突版本用例。记录来源、内容哈希与知识版本。
2. M3-02：知识文档与话术模板使用独立类型/集合；检索先限制适用业务、发布状态和有效期，再召回。分类不确定时追问或扩大经授权的业务范围，不强制错误过滤。
3. M3-03：实现原始查询基线和核心诉求改写方案；保留召回、排序与最终引用。embedding模型变更必须新建索引版本。
4. M3-04：用检索片段生成候选答复；后端验证引用确实来自本次授权召回的有效版本。无法可靠回答时返回 `needs_human` 或 `needs_clarification`。验证引用存在不等于证明所有语义正确，语义支持度纳入M6评测。
5. M3-05：记录坐席采纳、编辑、放弃与原因；这些记录是反馈，不自动等于正确标签。

交付：种子知识构建与导入脚本、索引清单、检索与建议API、三场景样例。

验收：每场景至少5条端到端用例；含正常、知识缺失、过期版本、条件不足和冲突知识。费率、时间、办理结果不由模型自行补足；候选答复可以打开引用原文。原问题与改写版本均可运行并留痕，不预写“提升”结论。

### M4：完成证据质检和人工复核闭环

入口：M2/M3通过；规则与数据模型见系统契约。

任务：

1. M4-01：在Ubuntu维护首版规则集，建议至少6条、覆盖三场景；每条包括适用范围、证据要求、风险级别、正反例与豁免条件。正式银行规则必须业务审核；演示规则标识 `demo_only`。
2. M4-02：默认规则包含：索取密码/验证码、无依据声称办理成功、无依据承诺减免费用、费用说明与有效条款冲突、阻碍投诉、明显侮辱性表达。缺少上下文或制度时输出证据不足；否定和引用他人话语不能按关键词直接判定。
3. M4-03：实现结构化模型判断、确定性规则检查和证据校验；问题绑定turn_id、原文区间、规则版本。评分仅在有效规则及扣分政策确定后计算；先保证逐项判断可解释。
4. M4-04：实现真实报告持久化、逐项确认/驳回/改判、必须填写理由、防重复提交和并发覆盖；保留原机器判断，人工修改另存。
5. M4-05：导出真实JSON和HTML报告；支持数据脱敏与权限校验。失败任务可查看原因并重试，重试生成新的运行记录。

交付：规则版本、质检任务、证据查看接口、复核API、真实报告导出。

验收：每条规则至少具备正例、反例、否定/转述、证据不足样例；错误证据区间被拒绝；提交→待复核→逐项处理→完成→导出→重启查询全链通过。两个复核员并发提交产生可解释的409冲突；系统故障不会伪装成零分或100分。

### M5：形成可操作的本地工作台

1. M5-01：提供登录、坐席工作台、质检列表/详情、知识审核、评测结果页；导航显示当前模型模式和环境。
2. M5-02：坐席页面展示会话、建议答复、来源及版本，支持采纳/修改；质检页面并排展示原文与证据，支持逐项复核。
3. M5-03：处理加载、空结果、失败、重试、无权限、长文本与重复点击；UI不能用静态假数据遮盖后端未完成能力。
4. M5-04：提供演示启动/停止/种子导入命令和8—10分钟演示脚本；重置数据命令只允许显式demo环境、再次指定目标，不接触生产库。

阶段出口：可标记“可演示版本”；尚不标记生产就绪。

### M6：在Ubuntu建立效果证据并优化模型

入口：M5通过；先固定任务定义和数据，再做优化。

任务：

1. M6-01：构建至少300条检索查询、180段质检会话作为首轮数据规模目标，三场景均衡；每场景至少20%覆盖正常/无答案/信息不足等困难样本。数量是计划目标，不是现有数据。
2. M6-02：按知识来源、会话模板家族和意图簇去重/分组，再按约60/20/20分为train/dev/test；同源改写同组。测试集冻结，模型与阈值只在train/dev调整；小样本规则报告实际分母。
3. M6-03：由人工复核检索相关性和逐规则标签；至少抽取20%双人标注并记录一致性。只有单人时如实记录为“开发者单人标注”，不声称双人一致性；本项目无业务人员可补验，不把模型自评当人工金标。
4. M6-04：比较原问题、现有情境拼接、核心诉求加过滤；比较规则基线、LLM基线、组合质检。记录Recall@5、MRR、无答案处理、引用支持度、逐规则Precision/Recall/F1、证据定位、延迟和调用成本。
5. M6-05：在Ubuntu输出失败分类，优先修数据、检索、提示词和规则。只有确认错误可由学习改善、数据足够、资源与费用明确时开展LoRA等微调；任务优先选意图分类或结构化质检之一，避免同时改所有环节。
6. M6-06：微调需记录基础模型来源/许可/版本、数据哈希、超参、随机种子、硬件、代码SHA、checkpoint与训练日志；训练先小规模dry-run，再完整运行。测试集不得用于训练或挑checkpoint。
7. M6-07：采用冻结测试集比较微调前后质量、严重问题漏检、成本和延迟。没有改善或资源不足时交付“保留基线”的实验结论；微调是条件任务，生产发布不以使用微调模型为前提。

交付：数据manifest、标注规范、数据拆分、评测脚本与报告、优化决策；若微调则另有模型卡、训练脚本和模型产物清单。

验收：`make eval EVAL_CONFIG=...` 在Ubuntu可复跑；报告含样本量、错误案例、模式、版本与原始结果路径。质量门槛见第7节。后续修改模型或规则需回归；测试集一旦参与调参，必须建立新的独立验收集。

## 7. 验收门槛与测量约定

以下为初始工程门槛，不是已达到的指标，也不是任何机构的正式验收标准。M0登记，M6前冻结评测口径；本项目没有业务方，因此不设业务阈值，工程门槛即最终门槛。执行模型不得为了让测试通过事后降低阈值。

| 项目 | 初始门槛 | 测量条件 |
|---|---|---|
| 必须通过的功能案例 | 100%通过 | 权限、版本、复核、失败状态等确定性测试 |
| 检索 | Recall@5 ≥ 0.85，MRR报告实测值 | 固定test，按场景分别统计，相关文档金标明确 |
| 无答案处理 | 正确拒答/追问/转人工比例 ≥ 0.90 | 独立无答案与条件不足子集 |
| 引用合法性 | 引用属于本次授权召回且版本有效的比例100% | 后端校验；与语义支持度分开 |
| 引用支持度 | 人工抽检关键事实被引用支持比例 ≥ 0.95 | 抽检至少50条；不足时全检并说明 |
| 质检 | macro-F1 ≥ 0.80；高风险规则Recall ≥ 0.95 | 逐规则报告分母、混淆矩阵；稀有样本附区间或注明证据不足 |
| 证据定位 | 精确原文片段校验100%；人工相关性 ≥ 0.95 | 无效位置返回待复核，不能丢掉失败样本后统计 |
| 普通API | P95 ≤ 500ms，错误率 < 1% | 非模型API，10并发、10分钟，记录环境与请求构成 |
| 候选答复 | P95 ≤ 15秒 | 每会话≤20轮、每轮≤500字，5并发；超时显式失败 |
| 质检任务 | 接收响应≤1秒，完成P95≤60秒 | 同上输入上限、5并发；依赖实际模型配额 |
| 可恢复性 | 初始RPO≤24小时、RTO≤2小时 | 测试环境恢复演练；业务方可要求更严格值 |
| 长时间运行 | 24小时定时探测，无未解释崩溃 | 真实Ubuntu服务；云模型探测频率遵守预算 |

Recall@K定义为相关知识版本进入前K候选的覆盖率，MRR使用第一个相关结果的倒数排名。质检以“会话×适用规则”为判定单元；证据不足、系统失败、解析失败另列比例和覆盖率，不能剔除后制造高分。阈值未达标时先保留失败结果，给出改进任务，再重验。

## 8. 每阶段统一交付规则

每阶段交付 `docs/milestones/Mx-report.md`，包含：任务ID、代码SHA、两端一致性、变更文件、验收逐条结果、真实执行命令、测试数量、失败/跳过原因、证据文件和风险。大日志/数据留Ubuntu，仓库只保存不含敏感信息的摘要与manifest。

`docs/implementation-status.md` 是唯一进度状态源：当前里程碑、当前任务、状态、两端SHA、已完成验证、下一次执行入口都只从这里恢复；不把进度拆散到 GitHub Issues（如需对外可见可镜像，但以文件为准）。

阶段状态只允许 `NOT_STARTED / IN_PROGRESS / BLOCKED / READY_FOR_ACCEPTANCE / ACCEPTED`。执行模型完成测试后标记READY_FOR_ACCEPTANCE；负责人确认后才为ACCEPTED。不得把“代码已写”视为验收通过。

实际使用的模型、数据、知识、规则、提示词和索引版本一起记录。实验中断后可凭运行ID恢复；失败实验也保留。每个完成式简历表述必须关联某次验收或实际使用证据。
