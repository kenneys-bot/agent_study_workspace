## 3. 实际能力和主要缺口

### 知识整理

已有问题抽取、意图分类、问题扩写、话术生成的模块和 API。可复用的是任务拆分和输入输出结构；尚不能称为受控知识发布系统。

阻断问题：`app/assistants/knowledge_base/intent_classifier.py:68` 的默认类别引用了当前常量中不存在的成员，默认构造会失败。`CallScript.format_full_script` 存在未定义变量问题，隔离执行可复现。需要补充知识来源、版本、生效时间、适用业务、审核状态，生成候选内容应经过审核才能用于正式回答。

### 检索与推荐

已有 Chroma 封装、情境分析、意图识别、候选话术推荐与重排代码。但主链存在可定位问题：

- `app/assistants/script_recommender/script_recommender.py:233` 将列表传给 `query_with_score`；`app/core/vector_db.py:249` 再包装成列表，形成嵌套输入。
- 推荐模块第 250 行将 `None` 传给重排，而重排第 189 行读取 `context.topic`。异常被捕获后退回原顺序，不能将该路径称为成功重排。
- 候选量扩大后未严格裁剪至请求数量，替身向量库测试中请求 3 条返回 6 条。
- `app/core/llm_client.py:155` 附近提取 system 消息后，实际调用只传非 system 消息，角色约束丢失。

建议将“核心诉求”“业务过滤条件”“表达语气”分开。情绪适合影响安抚语气，是否参与召回应由实验判断。不能预先宣布某种改写必然提升效果。

### 对话质检与复核

已有对话解析、LLM 分项评分、问题项和报告对象。属于通用文本质检原型，尚非银行规则驱动的可复核闭环。

- 对话解析存在文本分组、JSON 数组和时间戳类型问题，隔离复现可触发错误或丢失内容。
- `app/api/routers/quality_inspector.py:218` 起的报告导出构造固定评分报告，没有查询真实质检结果。
- 同文件第 260 行起提交复核仍构造模拟报告，第 272 行返回固定时间。
- `app/assistants/quality_inspector/report_generator.py:331` 将复核记录存于实例字典，API 依赖每次新建实例；跨请求不能形成持久化工作流。
- 内部复核 ID 带时间戳，接口返回 ID 不带，后续操作无法可靠引用同一任务。
- API 模型存在 evidence 字段，但质检响应映射没有传出该字段；还需要校验证据确实来自原文，而非仅补一个字段。

### 启动与工程交付

- 当前 Compose 启动 Python 容器中的 bash，未启动 API。
- Dockerfile 在复制 requirements.txt 之前安装它，干净构建存在阻断。
- 未发现可供坐席操作的完整业务前端；Swagger 接口文档不能代替业务演示。
- 文档列出的 PostgreSQL、Redis、监控、网关等不能据依赖声明认定已完成业务集成。
- 现有环境隔离执行 20 个纯单元测试，6 个通过、14 个因缺少 `pythonjsonlogger` 失败。这是环境阻断，不等于发现了 14 个独立业务错误。
- API 测试存在真实模型依赖，本次未运行。未验证 Docker 实际构建、真实模型结果和性能。

## 4. 银行业需求如何转化为项目能力

以下是产品设计建议，不是对该项目已满足监管要求的认证。

| 业务需求 | 建议实现 | 演示证据 |
|---|---|---|
| 客服口径准确且适时 | 知识版本、生效/失效状态、来源引用；无依据时转人工 | 同一问题在政策更新前后的引用变化 |
| 产品信息完整、避免不当承诺 | 适用业务规则检查，识别绝对收益承诺、遗漏关键说明等风险线索 | 风险项关联具体轮次、原文和规则版本 |
| 投诉处理有据可查 | 区分咨询与投诉诉求，形成待人工确认的处理记录 | 诉求、证据、责任角色、状态历史 |
| 客户信息受控 | 使用合成数据演示；角色权限、脱敏展示、审计记录 | 坐席与复核员看到不同操作权限 |
| 复核结论可追溯 | 人工确认/驳回及理由，保留模型判断与最终结论 | 重启服务后仍能查看处理历史 |
| 辅助效果可评价 | 固定评测集、基线对照、失败案例、延迟记录 | 一条命令重跑并生成结果表 |

依据：

- [银行保险机构消费者权益保护管理办法](https://www.nfra.gov.cn/cn/view/pages/rulesDetail.html?docId=1087524)：信息披露真实性、准确性、完整性和及时性，以及销售行为可回溯要求。检索结果可读，正文访问返回 403；正式固化规则前应核对完整条文及适用范围。
- [银行业保险业消费投诉处理管理办法](https://www.nfra.gov.cn/cn/view/pages/rulesDetail.html?docId=886173)：投诉统计分析与溯源整改。检索结果可读，正文访问返回 403。
- [银行保险机构数据安全管理办法（政府转载全文）](https://www.shanghai.gov.cn/rzfwgj/20251015/b3b1889cc6184cc688f867513f4f0939.html)：数据分类分级、必要授权和访问审计等要求。

监管条文、银行制度和项目演示规则应分别标记来源。将监管原则落实为具体质检条件，需要业务规则解释和适用条件，不能由模型随意生成。

## 5. 推荐的最小完整演示

建议用户为银行客服坐席与质检复核人员，主线为坐席辅助加会后文本质检。业务首选银行卡挂失咨询、信用卡费用/还款咨询、投诉受理三个场景。所有费率、时限和流程来自明确来源或标明虚构的演示制度。

演示流程：

1. 导入带来源和版本的演示知识，展示待审核与已发布状态。
2. 载入合成会话，例如客户不满费用并表示要投诉。
3. 提取核心诉求、检索有效知识，展示候选回答及引用。
4. 加入一段不当承诺或不完整答复，运行文本质检。
5. 展示问题对应轮次、原文片段、规则与判定理由；证据不足时标为待判断。
6. 复核员确认或驳回，填写理由，查看状态变化。
7. 导出真实报告；重启后确认记录仍在。

正常、知识缺失、模型超时、过期知识、未授权操作均应有可展示结果。不能将模型失败默认为质检合格，也不能将空检索结果伪装为可靠回答。

## 6. 候选技术路线与实施顺序

本节为待确认建议，不是已决定的技术选型。

- 保留 FastAPI 与已有模块边界，先修复入口、解析、模型消息、检索参数和重排序。
- 本地轻量版可使用 SQLite 保存知识版本、会话、报告、复核和操作记录；向量层沿用 Chroma。先完成持久化一致性，再讨论是否需要 PostgreSQL、Redis 与任务队列。
- 补浏览器工作台，提供坐席、质检、知识管理、评测四个明确入口。
- 模型模式显式区分：本地服务加云模型、本地真实推理、固定样例回放。回放只能证明流程与界面，不计入模型效果。
- 先以受控流程完成闭环。如果后续采用 Agent，需要明确工具选择、状态、终止条件和人工确认边界，再考虑在名称中加入 Agent。

顺序与验收：

| 阶段 | 交付 | 验收 |
|---|---|---|
| P0 修通基础链路 | 可启动服务、真实错误状态、核心缺陷修复 | 核心回归测试通过，启动步骤可复现 |
| P1 完成银行场景 | 有版本的知识、带证据的质检、持久化复核 | 三个场景端到端可操作，重启后数据仍在 |
| P2 形成展示产品 | 工作台、演示数据、报告导出、操作记录 | 约 8 分钟完成讲解，覆盖一个异常分支 |
| P3 建立效果证据 | 固定评测、基线/消融、失败分析 | 结果可重跑，有配置、版本、样本与耗时记录 |
| P4 整理求职成果 | 简历条目、架构图、演示脚本、追问材料 | 每个完成式表述都有代码、测试或交付记录 |

不承诺工期；工期取决于业务范围、模型方式、可用硬件和数据条件。

## 7. 评测与成果表达

检索对比：原始问题；现有情境拼接；核心诉求改写加业务过滤。使用同一知识版本、固定查询集和相关性标注，报告 Recall@K、MRR、无答案识别、引用有效性及延迟。按照知识来源或问题簇隔离开发集与测试集，避免同源改写泄漏。

质检对比：规则基线、LLM 基线、规则与 LLM 组合。按风险类别报告 Precision、Recall、F1、证据定位正确率、错误引用率及人工复核情况。加入否定、引用他人话语、历史陈述、信息不全、正常会话等易误判样本。缺少业务专家时明确标注为开发者标注的合成评测，不称为真实银行验收。

工程指标：请求成功率、P50/P95 延迟、并发条件、模型与机器配置、复核状态一致性、重启恢复。真实模型模式与回放模式分开统计。

成果证据应包括演示视频或脚本、可启动版本、知识与规则样本、真实导出报告、评测命令和结果、失败案例。完成后可写“完成本地部署与端到端验证”“在固定离线评测集验证……”。“生产上线”“服务多少坐席”“效率提升多少”需要真实业务证据，不能由本地展示推导。

## 8. 本轮待决定事项

1. 产品主线：推荐坐席辅助与会后文本质检，首版以内部人员使用为目标。
2. 业务范围：推荐先覆盖挂失咨询、信用卡费用/还款咨询、投诉受理。
3. 本地展示：推荐先允许本地应用调用云模型，同时保留显式回放模式；如要求完全离线，需要另行确认硬件与模型。
4. 历史边界：推荐把本次补齐标记为后续工程完善；需要用户说明原项目真实使用或交付到哪一步，以及希望突出算法还是应用工程能力。

术语表和 ADR 将在相应概念、关键权衡达成共识后记录，避免把当前提案伪装成已决策架构。

## 9. 补充核查与复现条件

- 当前推荐主要是检索已有话术，并非已有完整的“检索证据注入模型后生成回答”链路。知识和话术共用默认集合，推荐 API 又忽略 filters，存在将知识正文作为话术返回的风险。
- `question_generator.py:285` 附近的过滤函数没有验证传入的新生成问题，而是返回旧知识库查询结果；空库可能清空新生成结果。
- `api/routers/script_recommender.py:108`、153、203 附近分别存在 context、filters、context 未传入业务层的问题。
- `conversation_parser.py:126` 的正则分组取错内容；252 起 JSON 数组分支未定义 session_id；255 附近的时间戳字符串未转换为 datetime。以上均做过隔离执行复现。
- `auto_inspector.py:366` 起评分解析不接受“服务态度评分”等自然输出变体；模型异常在186附近转为默认零分报告。需要分开系统失败与业务不合格。
- `auto_inspector.py:425` 起独立合规解析将包含“违规”的否定表述也视为问题；解析不出分数时又可能默认100。该方法目前未由 inspect 接口接入。
- 语音模块没有真实 ASR 实现；不能列为首版已交付能力。
- 未使用 SDK 时的 mock 回复与随机 embedding 不等于本地真实推理；现有 mock 不能作为效果评测结果。
- `pythonjsonlogger` 已在 app 内依赖清单声明，当前失败是环境缺失；外层依赖清单与 app 内清单不一致。API 测试 mock fixtures 还依赖未声明的 pytest-mock。
- StringUtils.truncate 的测试期望保留5个内容字符再加省略号，实现却将省略号计入总长。需明确契约，不能盲目修改测试或实现。
