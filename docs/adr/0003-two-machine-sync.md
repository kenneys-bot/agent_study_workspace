# 同步是单向拉取：Ubuntu 不持有任何写凭据

状态：accepted（2026-11-12）

计划书 v1.0 假设双向 Git 同步。2026-11-12 实测：Ubuntu（`jack@192.168.1.27`，有线网卡 `192.168.5.10`）没有 GitHub SSH key，推送返回 `Permission denied (publickey)`；只能走 HTTPS 拉取（GitHub 约 2.7s，pypi 约 9s，出口经本机 Mihomo/Clash TUN）。决定：**Mac 是唯一推送方**；Ubuntu 只按指定 SHA `fetch` 并检出干净工作树，`make sync-check` 报告两端 SHA 与未提交状态；服务器不存任何可写凭据。服务器上若产生代码改动，改为在本机重做或把补丁带回本机合并——绝不在服务器上直接改主干。

## 考虑过的方案

- **在服务器放 deploy key**：能双向推送，但服务器一旦被入侵就拿到了仓库写权限，风险大于收益。
- **双向 rsync 覆盖文件**：会静默覆盖未提交修改，且无法解释两端 SHA 差异，直接排除。

## 后果

- GitHub 凭据不会出现在服务器上；「服务器改了但没同步回来」这类事故在机制上被消除。
- 代价：服务器端临时改代码不可行（可接受——核心代码都在 Mac 上写）。
- 服务器**没有 node/npm**：前端在 Mac 构建，或只在容器内构建；这条进 M5/M7 部署方案。
- 服务器是负责人日常使用的家用桌面机，且 GPU 被另一个训练任务占用：本项目在服务器上的构建/评测/容器都视为**分时借用**，重启整机前必须获得负责人逐次准许。
- 凭据（SSH 私钥、云模型 key、服务器 sudo 密码、GitHub token）一律不进仓库、不写进提交信息、不写进日志或文档；配置只留占位值。
